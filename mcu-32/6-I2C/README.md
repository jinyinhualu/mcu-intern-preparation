初次整理：2026-10-13；更新与基础理论收尾：2026-10-15。背景为 STM32F103；本页与[初始学习记录](../../study-log/2026-10-13.md)、[后续学习与收尾记录](../../study-log/2026-10-15.md)配套。完成的是理论问答、计算和局部源码阅读，尚未形成完整可运行驱动。

## 1. 功能地图与系统分工

I2C 用 SDA 数据线和 SCL 时钟线，使 STM32 可以选择一颗传感器、写入配置或读取测量结果。同一总线可连接地址不同的器件。

```text
CPU：组织操作、判断状态、解释测量值
             ↕ 数据寄存器 / 控制与状态
STM32 I2C 外设：串并转换、时钟、协议信号
             ↕ SDA + SCL
传感器：响应地址、接收配置、提供测量数据
```

本例 STM32 发起通信并产生时钟，因此是主机；传感器是从机。主机可以发送，也可以接收。角色由通信职责决定，不由器件是否“更重要”决定。

相同型号不意味着地址必须相同。是否能通过地址引脚或配置修改地址，须查器件数据手册；固定地址相同的两颗器件不能仅靠同一地址字节分别选中，可考虑独立总线或 I2C 多路复用器。

## 3. 开漏、上拉与基本标志

SDA 的高电平来自上拉。器件可以主动拉低线路，或释放线路；只要还有器件拉低，线路就保持低电平。正常数据位在 SCL 低时改变、在 SCL 高时稳定。

| 情况 | SCL 条件 | SDA 条件 | 意义或发出方 |
| --- | --- | --- | --- |
| 空闲 | 高 | 高 | 总线空闲状态 |
| START，S | 高 | 高 → 低 | 主机开始通信 |
| 重复 START，Sr | 高 | 高 → 低 | 未先 STOP，再进入寻址阶段 |
| STOP，P | 高 | 低 → 高 | 主机结束通信 |
| 数据 0 | 有效高电平期间 | 稳定低 | 当前发送方发送 0 |
| 数据 1 | 有效高电平期间 | 稳定高 | 当前发送方释放 SDA，发送 1 |
| ACK，A | 第九个时钟 | 低 | 当前接收方拉低，确认本字节 |
| NACK，NA | 第九个时钟 | 高 | 当前接收方释放 SDA，发送方也释放 |

![I2C 基本信号对照](assets/i2c-basic-signals.png)

Sr 的电气形态与 START 相同，区别在于它出现在尚未结束的通信中。它本身不携带读写方向。

## 4. 应答与结束是不同的操作

一个字节先发送 8 个数据位，高位在前；第九个时钟用于应答，由当前接收方决定 ACK 或 NACK，时钟仍由主机提供。发送方在应答位释放 SDA。

| 当前发送内容 | 接收方 | 第九位由谁决定 |
| --- | --- | --- |
| STM32 发送设备地址 | 被寻址的传感器 | 传感器 |
| STM32 写寄存器地址或配置 | 传感器 | 传感器 |
| 传感器向 STM32 发测量数据 | STM32 | STM32 |

在主机读取数据的场景中，中间字节 ACK 表示允许继续发下一字节，最后字节 NACK 表示本字节接收结束、不再要下一字节。不能把这一读场景解释推广成“任何 ACK 后都必须继续通信”。

```text
主机写最后一字节 → 从机 ACK → 主机 STOP
主机读最后一字节 → 主机 NACK → 主机 STOP 或 Sr
```

![图 241：字节应答与停止条件](assets/figure-241.png)

图 241 的 ACK 后出现 STOP 是有效的示意。它并不要求该字节一定是主机读取的最后一字节。

![写入 ACK 后 STOP 与读取 NACK 后 STOP](assets/i2c-ack-nack-stop.png)

NACK 是第九个时钟的高电平；STOP 必须有 SCL 高时 SDA 从低到高的变化。如果 SDA 在 NACK 时已经为高，主机需先在 SCL 低期间使 SDA 为低，再形成 STOP。第九位不是第九个数据位，也不是温度寄存器的写入指令。

## 5. 三类字节与方向选择

以下使用教学模型：设备 7 位地址 `0x48`，温度寄存器 `0x00`，配置寄存器 `0x01`，配置值 `0x02`。这些数值未对应已核对的真实器件。

7 位地址模式下，线上的首字节由设备地址左移一位，再加最低位 R/W 构成：

```text
设备地址 0x48 = 1001000
写方向：1001000 0 = 0x90，STM32 → 传感器
读方向：1001000 1 = 0x91，传感器 → STM32
```

读地址字节 `0x91` 仍由 STM32 发送；其后的数据阶段才由传感器发送。这是同一设备的两种操作。

| 字节类别 | 教学例子 | 回答的问题 |
| --- | --- | --- |
| 设备地址与方向 | 0x90、0x91 | 找哪颗器件，接下来谁发送数据？ |
| 寄存器地址 | 0x00、0x01 | 访问这颗器件内部哪个位置？ |
| 数据或配置值 | 0x02、高低字节 | 写什么内容，或读到了什么内容？ |

`0x00` 也是有效的发送字节，不表示“跳过发送”。使用 HAL/SPL 等接口时，还须核对函数要求传入 7 位地址还是移位后的地址，不能只凭线上字节机械填参；本轮未选择具体驱动库。

## 6. 写配置与读寄存器的完整序列

### 写配置：已讲解

```text
S → 0x90 → A → 0x01 → A → 0x02 → A → P
    选设备并写    选配置寄存器   写配置值
```

模型假设写方向中第一个数据字节选择寄存器，第二个数据字节写入配置。具体器件是否遵循该规则、是否自动递增地址，要看其数据手册。

### 读两字节：已讲解

```text
S → 0x90 → A → 0x00 → A → Sr → 0x91 → A → 高字节 → A → 低字节 → NA → P
    写方向       选择温度位置       读方向       STM32接收并应答
```

| 阶段 | 数据发送方 | 目的 |
| --- | --- | --- |
| 0x90 | STM32 | 选中设备，指定写方向 |
| 0x00 | STM32 | 写入寄存器选择信息 |
| Sr 后的 0x91 | STM32 | 重新寻址同一设备，指定读方向 |
| 两个测量字节 | 传感器 | 输出被选寄存器的数据 |

Sr 前已经是写操作，只是写入的是寄存器选择信息；Sr 后才切换为读取数据。Sr 让总线重新进入寻址阶段，方向由随后的地址字节最低位决定。它也可以用于继续写或寻址其他设备，不仅用于改成读取。

模型假设传感器在 Sr 后保留寄存器指针。重新寻址不等于重置内部指针；是否允许用 STOP 再 START 替代 Sr，同样由器件定义。同一写阶段连续写配置通常不需要 Sr。

## 7. 从线路字节到温度变量：已讲解基础

```text
传感器数据 → SDA → I2C 移位寄存器 → DR，RXNE=1
                                               ↓ CPU 读取
                                       high、low → raw → temperature
```

硬件收到字节后，普通变量不会因为 RXNE 置位而自动更新。在本轮不使用 DMA 的条件下，CPU 需要检查状态并读取 DR。不能默认刚读完第一个字节，第二个字节已经到达。

初始按及时取走每字节的简化流程讲解。后续已展开 DR/移位寄存器双缓冲：BTF 置位时，读一次 DR 后下一字节可转入 DR，RXNE 不一定清零，见第 12 节。接收收尾见第 13 节。

假设器件先发送高字节，再发送低字节，且数据是无符号 16 位：

```c
uint16_t raw = ((uint16_t)high << 8) | low;
// high=0x01、low=0x2C → raw=0x012C=300
```

假设零偏移、分辨率为 0.1℃/单位，CPU 可用 `raw * 0.1f` 得到 30℃。真实器件可能采用有符号值、其他分辨率或特殊位布局，换算须以数据手册为准。普通求和的错误在于没有保留高低字节位置，而不是“加法结果一定只有 8 位”。

## 8. 轮询、超时与状态接口：已讲解基础

一直轮询 RXNE 会占用当前程序流程。若始终没有数据，后续主循环任务无法继续；已启动的硬件 PWM 和允许执行的中断不因该等待自动停止。

软件超时是在程序中设定最大等待期限。SR1.TIMEOUT 对应 SMBus 的 SCL 低电平与累积时钟扩展条件，不能当作任何软件等待到期都会置位的通用标志。

接口应区分“这次读取是否成功”和“温度数值”。下面仅是教学接口，没有函数实现；约定只有完整读取成功才更新输出变量。

```c
typedef enum {
    TEMP_OK,
    TEMP_TIMEOUT,
    TEMP_ERROR
} TempStatus;

TempStatus ReadTemperature(float *temperature);

// 放在调用函数内部：
// float temperature = 30.0f;  // 上一次成功结果
// TempStatus status = ReadTemperature(&temperature);
// if (status == TEMP_OK) {
//     使用本次结果；
// } else {
//     温度仍可能是旧值，本次结果未成功更新；
// }
```

`&temperature` 提供变量地址，让函数能够通过指针写回数据。是否在失败时保持旧值由接口约定和实现保证，不能假设所有现成驱动都如此。

| 返回状态 | 温度变量 | 判断 |
| --- | --- | --- |
| TEMP_OK | 0.0℃ | 成功读到 0℃ |
| TEMP_OK | 30.0℃ | 成功读到 30℃ |
| TEMP_TIMEOUT | 保留旧值 30.0℃ | 本次读取超时，不能当作新测量 |

先检查 `status`，确认成功后再使用数据作为本次结果。已有串口 `UART1_ReceiveByte(&byte)` 也采用返回状态、指针输出数据的形式；该串口函数仍是无限阻塞，未实现超时，且接收错误时可能仍输出字节，具体契约与本教学温度接口不同。

## 9. 非阻塞、超时与进度保存：已讲解，未实现

加入超时避免永久卡住，但等待期间仍可能占住当前流程。假设下面的函数内部最多轮询等待 20 ms：

```c
status = ReadTemperature(&temperature);
ScanButtons();
```

用户已正确回答：在这段等待期间，不能执行后面的 `ScanButtons()`。函数返回后才能进入下一条语句；有限超时仍然会阻塞当前调用流程。

非阻塞把操作拆成阶段，每次检查做当前能做的事情，尚未完成就返回主循环。返回不等于整笔交易结束，下一轮继续检查同一操作，不重新发起读取。

```text
开始一次读取 → 检查进度 → 扫描按键 → 下轮检查同一次读取
                     ↓
          进行中 / 成功 / 失败
```

起始时间在本次操作开始时记录，后续以“当前时间−本次起始时间”计算等待期限。每次检查都重置计时，会导致长期无法超时。已经发现无应答等确定错误时，不需要等满超时才处理。

跨轮保存需要持续存在的上下文：

| 数据 | 用途与处理 |
| --- | --- |
| 当前状态 | 区分等待地址、等待数据、收尾等阶段 |
| high、low | 保存已收到的临时数据，不能每次检查重新清零 |
| start_tick | 保存本笔交易的起始时间 |
| temperature | 保存上次有效结果，完整成功后才更新 |

普通自动局部变量不能用于函数返回后的持续保存。static 局部变量只初始化一次，作用域仍在函数内；也可用持续存在的上下文结构体。新操作开始时主动重置相关状态，忙时不直接覆盖当前交易。这里是软件设计示意，未实现完整状态机。

非阻塞不代表可以任意延迟所有硬件操作。F1 的部分接收尾部序列需连续及时执行；不能把每条寄存器操作都机械拆到任意下一轮主循环。

## 10. TMP102 正常模式的换算：已讲解并做题

此前 0.1℃/单位为假设。TMP102 正常模式（EM=0）为 12 位有符号补码，单位 0.0625℃，先发高字节，数据占两字节高 12 位，低 4 位为 0。扩展模式不同，本轮不展开。

```text
两个字节： [温度高8位] [温度低4位 | 0000]
拼接16位 → 右移4位 → 解释12位补码 → 乘0.0625℃
```

下面仅是正常模式的数据处理片段，假设 high、low 已通过一次成功的读取取得：

```c
uint16_t combined = ((uint16_t)high << 8) | low;
uint16_t raw12 = combined >> 4;

/* raw12在0～4095之间；先转为有符号32位再减，避免无符号减法回绕。 */
int32_t signed_raw = (int32_t)raw12;
if ((raw12 & 0x0800U) != 0U) {
    signed_raw -= 4096;
}

float new_temperature = (float)signed_raw * 0.0625f;
```

| 字节 | 右移后的无符号值 | 12 位有符号值 | 温度 |
| --- | ---: | ---: | ---: |
| 0x1E、0x00 | 480 | 480 | 30℃ |
| 0xFF、0x00 | 4080 | 4080−4096=−16 | −1℃ |
| 0xFF、0x60 | 4086 | 4086−4096=−10 | −0.625℃ |

符号位看有效数据的 bit11，不看 16 位容器的 bit15。用户已完成右移与负温度变式题，但未独立实现完整器件驱动。

本节只确认 TMP102 的温度数据格式，不把前文教学配置值 0x02 当作已核对的 TMP102 配置。

## 11. 从总线事件到 STM32 标志

| 当前阶段与事件 | 标志 | 软件动作 |
| --- | --- | --- |
| START 或 Sr 发出 | SB=1 | 读 SR1，再向 DR 写设备地址字节 |
| 主机发送设备地址，收到 ACK | ADDR=1 | 按收发方向和长度完成地址阶段处理 |
| 主机发送地址或数据，收到 NACK | AF=1 | 停止推进正常流程，进入错误收尾 |
| 发送时 DR 空 | TxE=1 | 可以装入下一字节，不代表当前线路字节必定已发完 |
| 接收时 DR 非空 | RXNE=1 | DR 有可读的完整字节 |
| 字节传输及缓冲达到对应条件 | BTF=1 | 按当前发送或接收流程推进，不能单凭它认定整次交易成功 |

ADDR 表示地址获得应答，不表示温度数据到达。主模式下收到 NACK 不置 ADDR。写方向通常按先读 SR1、再读 SR2 清除 ADDR；读方向还需要结合接收长度提前配置 ACK/POS/STOP。

```text
Sr → STM32发送0x91 → 传感器ACK → ADDR=1
                          ↓ 地址阶段处理完成
               传感器发数据 → STM32给ACK/NACK
```

`0x91` 由主机发送，应答方是传感器；其中 R/W=1 选择的是后续数据阶段方向。字节都经 DR 传递，但设备地址、寄存器选择、温度数据的含义由阶段与器件定义决定。

## 12. RXNE 与接收 BTF：双缓冲关系

**BTF 是 Byte Transfer Finished，发送和接收都使用。**中文名称“字节发送结束”不代表它只适用于发送。

```text
SDA → 移位寄存器（逐位接收） → DR（有效低8位） → CPU
```

以下限定正常主接收、允许硬件延长 SCL、CPU 尚未读取 DR：

| 当前内容 | RXNE | BTF |
| --- | ---: | ---: |
| DR 无可读数据，首字节尚未完整进入 DR | 0 | 0 |
| 首字节在 DR，第二字节尚未完整收到 | 1 | 0 |
| 首字节在 DR，第二字节在移位寄存器完成接收 | 1 | 1 |

在后一个状态中，硬件保持 SCL 低，等待软件处理。若没有后续第三字节：

| CPU 操作后 | DR | 移位寄存器 | RXNE |
| --- | --- | --- | ---: |
| 尚未取数 | 第一个字节 | 第二个字节 | 1 |
| 第一次读 DR | 第二个字节转入 | 空 | 1 |
| 第二次读 DR | 空 | 空 | 0 |

因此连续读取同一个 DR 能取出先后两个字节；不是 DR 同时保存 16 位数据。RXNE/BTF 不记录整笔交易的字节序号，字节计数仍由软件保存。

## 13. 接收尾部：单字节、两字节与多字节

### 两字节：已结合手册与 HAL 分支解释

协议目标：第一字节 ACK，第二字节 NACK，然后 STOP。

ACK/NACK 由外设按事先设置，在第九个时钟执行。CPU 读取 DR 晚于线路接收和应答；检测到接收 BTF 后，不能再改变已经发出的应答。

| 控制 | 用途 |
| --- | --- |
| ACK | 设置接收时应答方式 |
| POS | 调整 ACK 设置作用于当前还是下一个接收字节，用于两字节安排 |
| STOP | 请求硬件产生停止条件，不等于写入瞬间线路已停止 |

沿用所核对 HAL 两字节分支，开始时允许 ACK：

```text
读地址获得应答，ADDR=1
        ↓
设置POS，在规定的紧密时序内清ADDR、清ACK
        ↓
第一个字节ACK，第二个字节NACK
        ↓
等待BTF：两个字节在硬件缓冲中
        ↓
请求STOP，读取DR两次，完成后续收尾
```

POS、ACK 必须在规定阶段设置，不是只要“比 BTF 早”就一定正确。库代码对清 ADDR/ACK、STOP/首次读 DR 等关键操作保护执行时序。这里没有给出可直接复制的完整底层驱动，也未处理所有异常分支和后续控制位恢复。

### 单字节：已讲解功能区别

唯一的数据字节就是最后字节，应提前安排 NACK，并按单字节时序配合清 ADDR、请求 STOP；等待 RXNE，再读取 DR 一次。不能照搬两字节等待 BTF 的流程，否则正常单字节操作可能一直等不到那个双缓冲条件，最后软件超时。

### 多字节：已讲协议规则，精确尾部实现待实践

```text
字节1 ACK → 字节2 ACK → 字节3 ACK → 字节4 NACK → STOP
```

前面的字节可以按 RXNE 取走，最后三个字节有 F1 专门的收尾安排。本轮未展开这部分精确寄存器顺序，不记为已会实现。第三字节若提前 NACK，影响的是第四字节继续接收，第三字节本身仍可有效。

## 14. 无应答、错误收尾与完整结果

STM32 作为发送方时，不仅设备地址要检查应答，寄存器地址和配置字节也一样。比如 `0x90` 获 ACK，但 `0x00` 获 NACK，不能认为寄存器已成功选择并继续正常读取。

当前主发送器无应答场景：

```text
发现AF → 停止推进后续读写 → 请求STOP并清理相关状态 → 报告失败
```

`return TEMP_ERROR` 只改变 CPU 程序流程，不能代替硬件收尾。不同错误需不同处理；仲裁丢失后不能照搬仍拥有总线时的 STOP 流程，完整恢复待实践。

| NACK 场景 | 意义 |
| --- | --- |
| 传感器对主机发来的设备地址/寄存器地址给 NACK | 该字节未获应答，按失败收尾 |
| STM32 对完整读取的最后一个字节给 NACK | 正常表示不再需要下一字节 |

完整两字节接收、正常 STOP、无其他错误后，可报告成功并更新温度；失败则保留旧有效温度并报告错误。完整数据与正常收尾缺一不可，不能只凭某一个标志或某个数值判断成功。

## 16. 纠正重点、教学方式与验证边界

- 主机角色由通信职责判断；接收数据时主机仍是主机。
- ACK/NACK 的发出方随接收方变化；一个字节不需要先 ACK 再 NACK。
- ACK、NACK 与 STOP 各自承担不同作用；主机写完可在 ACK 后 STOP。
- Sr 前的 0x90 已有写方向；0x00 是寄存器选择信息；Sr 后方向由 0x91 决定。
- DR 中有数据不等于 CPU 已更新变量；拼接与温度换算由软件完成。
- 温度值不能证明本次读取成功；先检查返回状态，成功读到 0℃也是有效结果。

- BTF 不限于发送；RXNE=1 已说明 DR 有完整数据，不能因 BTF=0 否定它。
- 两字节缓冲时第一次读 DR 后，第二字节转入 DR，RXNE 可以继续为 1。
- 0x91 的应答由传感器给出；主机接收最后字节的正常 NACK 不意味着读取失败。
- ACK/NACK 要提前安排，软件看见状态标志后不能更改已经过去的线路应答。

学习节奏采用“先讲一个小主题，再提问检验”。用户曾反馈从字节发送突然跳到宏观工程感到迷失，后续按总线、外设、软件三层明确连接，避免继续堆叠状态机细节。
