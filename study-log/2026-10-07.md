## 实际完成

### 1. 硬件路径与 DR 的读写含义

重新建立了收发两条独立路径：

```text
发送：CPU 写 DR → 发送数据寄存器 TDR → 发送移位寄存器 → TX 引脚
接收：RX 引脚 → 接收移位寄存器 → 接收数据寄存器 RDR → CPU 读 DR
```

STM32F1 代码中的 `USART1->DR` 是收发共用的访问地址：写访问内部发送存储，读访问内部接收存储。RDR/TDR 用于描述内部不同的数据存放位置，不需要额外找一个 RDR 地址。移位寄存器负责逐位收发，数据寄存器负责交接完整数据。

### 2. 初始化与波特率

- USART1 使用 APB2 上的 `PCLK2`；计算波特率不能无条件使用 SYSCLK。
- PA9 是 TX，配置为复用推挽输出；本例 `CRH bit 7:4 = 0xB`，即 `CNF=10、MODE=11`。
- PA10 是 RX，配置为浮空输入；本例 `CRH bit 11:8 = 0x4`，即 `CNF=01、MODE=00`。
- GPIO 的 50 MHz 是输出驱动速度档位，不是 UART 波特率。
- `CR1/CR2/CR3` 保存控制配置，`SR` 反映状态；`CR1=0` 主要禁用并重建控制配置，不会清除所有 SR 错误标志。
- `UE/TE/RE` 开启 USART、发送器和接收器；`M=0、PCE=0、STOP=00` 对应 8N1。
- 程序指令通常存放在 Flash；普通变量在 SRAM，外设配置与状态在外设寄存器。执行 Flash 中的指令不等于把所有数据写回 Flash。

纠正了直接计算 BRR 后又多乘 16 的错误：

```text
USARTDIV = PCLK2 / (16 × baudrate)
BRR 编码值 = round(16 × USARTDIV) = round(PCLK2 / baudrate)

36 MHz / 9600 = 3750 = 0x0EA6
USARTDIV = 234.375，整数部分 234、小数字段 6
```

在 BRR 固定为 3750 时，正确回答 PCLK2 从 36 MHz 增加到 72 MHz，实际波特率变为 19200。

### 3. 阻塞式收发与状态快照

| 标志 | 为 1 时的含义 | 对应操作 |
| --- | --- | --- |
| TXE | 发送数据寄存器空，可提交下一个字节 | 写 DR |
| TC | 当前硬件中的发送已完成，最后一个停止位发完 | 结束整段发送等待 |
| RXNE | 接收数据寄存器中有未取走的数据 | 读 DR |
| ORE | 发生接收溢出，至少丢失过数据 | 保存 SR，再读 DR 处理 |

- 没有接收数据且没有超时机制时，`ReceiveByte()` 会一直等待 RXNE，后面的回显和 LED 操作执行不到。
- A 已在 RDR、CPU 尚未取走，B 又接收完成：RDR 保留 A，`RXNE=1、ORE=1`，B 丢失，无法通过后续读取恢复。
- 接收先把 SR 复制到普通变量，再读 DR。硬件错误标志被清除后，普通变量中的状态副本不会自动改变。
- 在上述 A/B 溢出例子中，`byte` 得到 A，但 `UART1_ReceiveByte()` 的返回状态包含溢出错误，不能因为取得 A 就判断为 OK。
- 清除 ORE 不会恢复丢失的数据；本机 TC=1 也不能证明对方正确收到数据。

### 4. 函数补写与执行顺序回测

在给定函数框架和已有例程基础上，提交了以下核心代码：

```c
/* 单字节发送：交给硬件后返回，不等待线路发送结束。 */
while ((USART1->SR & USART_SR_TXE) == 0U) {
}
USART1->DR = (uint16_t)byte;

/* 单字节接收：先保存状态，再取数据。 */
while ((USART1->SR & USART_SR_RXNE) == 0U) {
}
status_register = USART1->SR;
*byte = (uint8_t)USART1->DR;

/* 整段发送：逐字节提交，最后确认线路发完。 */
for (index = 0U; index < length; ++index) {
    (void)UART1_SendByte(data[index]);
}
while ((USART1->SR & USART_SR_TC) == 0U) {
}
```

整段发送补写中包含了非零长度下的空指针检查；经提示确认循环变量需要声明。能正确回答回显的四个步骤：等 RXNE、读 DR、发送前等 TXE、返回前等 TC。

最后重点纠正 TC 的含义：它只知道当前硬件是否发送完成，不知道软件数组中还有 B、C 等后续字节。A 已发完而 B 尚未提交时，TC 可以为 1；之后通过现有 `SendByte()` 的“读 SR、写 DR”序列提交 B，会清除 TC，不需要额外手动清零。

因此逐字节等待 TC 也能正常发送，只是下一个字节不能提前装入，可能增加字节间空闲间隔。字节之间等 TXE、整段结束等 TC 能利用硬件的发送流水过程。

### 5. 非阻塞、中断与缓冲区的职责

- 非阻塞轮询在 RXNE=0 时返回“暂无数据”，让主循环继续处理按键等任务；这不会增加硬件接收容量。
- 即使非阻塞，主循环长期不读 DR，仍然可能产生 ORE。
- 接收中断负责及时读 DR、保存字节并快速返回；主循环负责解析命令和执行业务。中断返回后，继续执行之前被打断的主循环代码。
- 耗时解析即使没有调用延时函数，也会占用中断处理时间；同一个串口中断不能抢占自己，后续数据可能来不及取走。
- 若在中断中调用依赖 SysTick 的 `HAL_Delay()`，且 SysTick 无法抢占该中断，计时可能无法推进，延时不能结束。
- 硬件 ORE 是 DR 没被及时读取；软件缓冲区满是 DR 已读取，但取出的数据没有足够空间保存。软件满不一定使硬件 ORE 置位。
- 缓冲区满后可以拒绝新数据或覆盖旧数据，具体取决于实现，不能认定必然覆盖历史数据。
- 115200 baud、8N1 下每字节约 86.8 us；空的、有效容量为 64 字节的缓冲区约 5.56 ms 就能积满，前提是连续发送、主循环不取数据、中断持续及时运行。
- 若每秒收到 1000 字节而只能处理 500 字节，每秒积压 500 字节；扩容只会推迟溢出，需要提高处理速度、降低发送速度或让发送方暂停。
