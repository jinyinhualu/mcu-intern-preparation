## 实际完成

### 1. 主机、从机与电气关系

最初把 STM32 判为主机的理由是“没有 STM32 就驱动不了传感器，所以 STM32 更重要”。讲解后转向按通信职责判断：本例 STM32 发起通信并产生时钟；传感器响应地址。主机既可以发送，也可以接收，接收时仍是主机。

学习了 SDA 的开漏与上拉关系：器件主动拉低，释放后由上拉使总线回到高电平；只要仍有器件拉低，线路就不会变高。“释放线路”不等于主动输出高电平。

讨论了同型号传感器的区分：使用不同设备地址；可配置地址的器件依其地址引脚或配置区分。若同一总线上固定地址完全相同，单靠地址字节不能分别选中，需要独立总线或多路复用等方案。具体地址能力待真实器件数据手册确认。

### 2. 基本标志与第九个时钟

通过表格和图示学习了空闲、START、重复 START、STOP、数据 0/1、ACK、NACK。正常数据在 SCL 低时改变、在 SCL 高时稳定；START 和 STOP 是 SCL 高期间的 SDA 特殊变化。

用户曾认为一个字节结束需要“先 ACK 再 NACK”，随后主动纠正为第九个时钟中的两种情况。接收方拉低 SDA 表示 ACK，释放 SDA 且总线为高表示 NACK；发送方在应答位应释放 SDA。

读传感器数据时，STM32 是接收方：还有下一字节时给 ACK，最后一字节给 NACK。用户能解释“这个字节已经读完，不再要下一个了”。发送设备地址或向传感器写数据时，传感器才是接收方并给应答。

### 3. ACK、NACK 与 STOP 的区别

用户根据手册图 241 提出：既然 ACK 表示还需要数据，为什么图中随后出现停止条件？由此区分了应答与结束通信：

- ACK 表示本字节被接收，并不要求主机一定继续发送。主机写最后一字节后，从机 ACK，主机随后 STOP 是正常情况。
- 主机读取最后一字节时给 NACK，随后再产生 STOP 或 Sr。
- NACK 是第九个时钟期间的高电平，STOP 是 SCL 高期间 SDA 从低到高的变化，二者不是同一种信号。
- 第九位是应答位，不是新的数据位；字节接收、进入 DR 与应答过程由硬件按时序配合，并非由第九位选择“是否把温度写入寄存器”。

用户曾在“STM32 给 ACK”后推断一定不会随后 STOP，此处已纠正，仍需间隔复习。

### 4. 设备地址、寄存器地址与读写方向

在假设设备 7 位地址为 `0x48` 的例子中，用户正确计算线上写地址字节为二进制 `10010000`，即 `0x90`，并理解 `0x90/0x91` 是同一颗传感器的写/读操作。

用户曾认为 Sr 前只有传感器地址，没有读写方向，Sr 后才真正开始读写。经纠正，明确第一次地址字节最低位 0 已经选择写方向：STM32 向传感器发送寄存器选择信息；第二次地址字节最低位 1 选择读方向：传感器向 STM32 发送数据。

用户也曾把发送 `0x00` 理解为“不进行本次发送”，随后正确回答它是传感器内要访问的寄存器地址。区分了 `0x00` 这个有效字节与“什么都不发送”。

讨论的两条教学序列：

```text
读取两字节：S 0x90 A 0x00 A Sr 0x91 A 高字节 A 低字节 NA P
写配置：    S 0x90 A 0x01 A 0x02 A P
```

用户能在提示下区分设备地址、寄存器地址和配置值，也能回答读方向由 `0x91` 的最低位 1 决定。模型假设寄存器指针在 Sr 后保留；Sr 本身让总线进入新的寻址阶段，不等于清空传感器内部指针。

### 5. DR、RXNE 与 CPU 处理

用户正确指出接收字节对应 DR 数据寄存器与 RXNE 标志。硬件收到数据，不等于 CPU 已经执行读取语句或更新普通变量；在没有 DMA 等搬运机制的讨论条件下，CPU 需要检查标志并读取 DR。

用户能回答应先检查 RXNE 是否置位，不能默认下一字节已经到达。本轮主要按及时读取每个字节的简化流程讲解。手册还说明 BTF 时读一次 DR 后 RXNE 可能仍为 1，因此“读 DR 一定使 RXNE 变 0”不能作为普遍规则；具体缓冲时序待后续学习。

对高字节 `0x01`、低字节 `0x2C`，用户能判断需要拼接而不是普通求和：

```c
uint16_t raw = ((uint16_t)high << 8) | low; // 0x012C = 300
```

用户最初说“直接相加只能得到一个字节”，此表述已纠正：和的范围取决于类型与数值，关键是普通相加没有把高字节放到高 8 位。在假设无符号、零偏移、每单位 0.1℃的教学条件下，用户正确回答 300 对应 30℃，换算由 CPU 完成。

### 6. 阻塞、软件超时与数据有效性

用户能解释 RXNE 始终为 0 会卡在等待循环中，后面的主循环任务也不能继续。讨论限定的是当前程序流程；硬件 PWM 和已允许的中断不因此自动停止。

用户曾认为等待超时就会使 SR1.TIMEOUT 置位。已区分：软件设置的等待期限与 SMBus 的 SCL 低电平/累积时钟扩展超时条件不同，任意一次软件等待到期不保证硬件 TIMEOUT 置位。

读取失败时，变量可能保留上一次的 30℃，不能作为本次新读数。直接用温度值 0 表示失败也会与成功读取 0℃混淆。借助已有串口接口，引入如下教学约定：返回状态，指针输出温度，只有读取完整成功才更新温度。

```c
TempStatus status = ReadTemperature(&temperature);
if (status == TEMP_OK) {
    // 使用本次成功更新的数据
}
```

用户先回答应检查 `temperature`；纠正为应检查 `status`。最后回测：`status == TEMP_OK` 且 `temperature == 0.0f`，用户正确回答“读取成功”。这属于刚纠正后的理解证据，尚未实现接口或独立编写调用流程。
